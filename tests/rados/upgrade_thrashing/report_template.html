How to Read This Report

Expand guide to chart terminology and interpretation

Daemon Upgrade Waterfall

A Gantt-style chart showing when each daemon type was upgraded. Each colored band represents one daemon type's total upgrade window. Hover over bands for details.

Orch Window vs Redeploy Window

Orch Window (dashed border): The full orchestrator operation time, from when ceph orch upgrade begins scheduling the daemon type until all instances report the new version. This is the period during which IO impact is expected.

Redeploy Window (solid border): The narrower container redeploy phase within the orch window, when daemon containers are actually stopped and restarted with the new image.

Lifecycle Events

Vertical dashed lines within per-daemon IO charts mark key moments:

  • Upgrade Start (orange): When the orchestrator begins the upgrade for this daemon type
  • Upgrade Complete (green): When all instances of this daemon type are running the new version
  • Individual daemon markers (faint lines): Per-instance redeploy timestamps

IO Impact Analysis

IOPS: Input/Output Operations Per Second across all pools. Throughput: Aggregate cluster MB/s (all pools).

Each per-daemon card shows cluster-wide all-pool IOPS and throughput during a ±2 minute window around that daemon type's upgrade (not per-daemon IO). Look for dips during the upgrade window and recovery afterward.

IOPS Impact %: Percentage change in average IOPS during a daemon's upgrade window compared to the pre-upgrade baseline. A positive value (shown as "+X% rise") means IOPS increased during that window, typically because the daemon type has minimal IO impact. A negative value (shown as "X% drop") means IOPS decreased during the upgrade -- larger absolute values indicate greater IO impact. Color coding: green = minimal impact (<=10% drop or any rise), amber = moderate impact (10-30% drop), red = significant impact (>30% drop).

Version Convergence

Shows how quickly daemons converge to the target version over time. A steep curve indicates fast, parallel upgrades; a staircase pattern shows sequential daemon-type upgrades.

Health Timeline

Horizontal bar chart showing all Ceph health warnings observed during the upgrade. Each bar spans from when the warning first appeared to when it was last seen. Color-coded by severity: blocking (red) = errors that stopped the upgrade, concerning (orange) = warnings not expected during normal upgrades, expected (blue) = transient warnings normal during rolling upgrades. Use the toggle to show/hide expected and informational warnings.

Crash Details

Appears only when daemon crashes were detected. Lists affected daemons, assert messages, and backtraces from ceph crash info, plus matching events from daemon log scans when crash dumps were not archived.

Feature Verification

Post-upgrade feature checks. PASS = feature enabled and verified. FAIL = feature could not be enabled or verification failed. SKIP = feature not applicable to this configuration or version.

Data Integrity

End-to-end data integrity verification using checksums written before the upgrade and re-verified after.

  • CRC32c checksums are embedded in files across CephFS (kernel/FUSE), NFS (v3/v4.x), and RBD block devices
  • MD5 hashes are stored as RADOS object xattrs for pool-level integrity checking
  • Mismatch = checksum disagreement (possible data corruption) — fails the hop
  • Verify warn = mount skipped / unverifiable (stale, hung, no output) — not corruption; does not fail the hop

Data Collection Methodology

    

      
Timeseries data in this report is collected from the cluster's built-in Prometheus monitoring stack, with CLI fallback at phase boundaries.

      
    
        
  • Primary source: Prometheus HTTP Query API (query_range) -- queried once at report generation time for the entire test window
    • 
        
  • Resolution: 10-second scrape interval (matching cephadm default Prometheus configuration)
    • 
        
  • Fallback source: Direct CLI commands (ceph health detail, ceph versions, ceph fs status) captured at phase boundaries for metrics without Prometheus equivalents
    • 
        
  • Daemon lifecycle events: Parsed from host daemon logs under /var/log/ceph/{fsid}/, merged with cephadm deploy events (deploying, scheduled_upgrade). Cards marked orch-only lacked logfile data.
    •
